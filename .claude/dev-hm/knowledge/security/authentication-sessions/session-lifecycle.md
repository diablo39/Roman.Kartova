# Authentication and session integrity — Session lifecycle

Section of `knowledge/security/authentication-sessions.md`.


Our session layer gives every session an honest beginning and a definite end:

- A fresh session identifier is issued when the principal authenticates, and the pre-login
  identifier stops reaching an authenticated context (SEC-014). Both halves matter: rotation
  without invalidation still honors the old identifier, so an identifier handed out before login
  could carry the authenticated session. The control test asserts both — new identifier issued,
  old identifier refused.
- Identifiers are generated by the platform CSPRNG at full length (SEC-033), carry no encoded
  meaning, and are stored and compared server-side.
- Sessions expire twice over: an inactivity timeout that ends abandoned sessions, and an
  absolute lifetime that ends even active ones, forcing re-authentication on a cadence matched
  to the application's risk. Both bounds are server-enforced; a client-side timer is a courtesy,
  not a control.
- Logout is a server-side act: the session record is deleted or invalidated, not merely the
  cookie cleared. The control test presents the old cookie after logout and asserts refusal —
  checking that the client forgot it proves nothing about the control.

Server-side sessions are revocable by construction, which is why they remain the default for
browser-facing applications. Stateless tokens trade that property away and must buy it back with
the revocation design below — choose per surface, and record the choice.
