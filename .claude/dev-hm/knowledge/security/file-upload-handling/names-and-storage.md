# File upload handling — Names and storage

Section of `knowledge/security/file-upload-handling.md`.


The stored name is generated by us — a CSPRNG-derived identifier or UUID — and the mapping to
the client's filename lives in the database, where the original name is display data: encoded
on output like any external string (SEC-003, SEC-043), never concatenated into a path or shell
command. This one decision removes path traversal via filename (SEC-045), name collisions and
overwrites between principals, guessable-URL enumeration, and stored-name injection at once.

Storage is somewhere the platform will never execute or template: an object store, or a
directory outside the web root on a filesystem mounted without execute permission. The web
server serves uploads only through our handler (or signed object-store URLs — below), never by
mapping the upload directory as static content. Even with generated names, the write path
canonicalizes and verifies containment before any filesystem operation — defense in depth for
the day someone reintroduces a user-influenced path segment.
